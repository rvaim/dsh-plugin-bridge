# 架构与界面优化审查

本轮基于当前 `0.6.0` 工作区。上一轮 DSH 迁移改动保留；解析器、三个协议实现、统一解析模型和解析测试均为保护范围。本文区分已实施的客户端优化与后续核心建议，避免把建议写成已经完成的改造。

## 优先结论

目前已经具备合理的单向依赖：协议模块 → 统一契约/模型，管理层 → 解析契约，运行层 → 统一执行模型，装配层 → 具体实现。八种解析器组合验收应继续保留。没有必要再次重排整个项目或把这些边界合并成一个公共目录。

当前最值得处理的是：远端操作占用仓库锁、临时来源清理的所有权边界、仓库读取中的运行副作用，以及浏览器页面同时负责异步状态和所有展示。本轮直接实施最后一项，并改善对应 UI；前三项保留为后续独立变更。

## 核心与 Host 的解耦建议

| 优先级 | 已核实位置 | 问题与影响 | 建议边界与验收 |
| --- | --- | --- | --- |
| P1 | [manager.ts:860](../src/manager/manager.ts#L860)、[manager.ts:896](../src/manager/manager.ts#L896) | `checkUpdates()` 在仓库锁内逐个探测远端；`list()` 也需要同一锁。慢来源可能阻塞读取和其他生命周期操作。仅让 UI 并行请求不能消除服务端锁竞争。 | 先将更新检查改为短锁读取来源快照、锁外探测、返回所检查的 revision。安装/更新事务继续保守保留提交锁。用可控慢探测测试证明列表和不相关操作能继续；提交前重验 revision，禁止仅删除锁。 |
| P1 | [gateway.ts:228](../src/web/host/gateway.ts#L228)、[manager.ts:395](../src/manager/manager.ts#L395)、[manager.ts:481](../src/manager/manager.ts#L481) | 多插件选择请求保存创建时的 `sourceCreated` 标志；等待选择期间同来源可能被另一调用升级为显式来源，而取消仍调用无所有权限制的 `sourceRemove()`。这会混合“回收临时隐式来源”与“用户主动删除来源”的权限。 | 增加管理层原子操作“仅在仍为 implicit 且无引用时回收”，在同一锁内重读 ownership/引用。显式删除保留自己的 API。定向覆盖：beginAdd → sourceAdd 同来源 → cancel/过期，显式来源必须保留；并发选择转交清理责任仍正确。 |

另外两项 P2 结构建议：

- [source-update.ts:25](../src/manager/source-update.ts#L25) 的 `SourceUpdateHost` 同时携带 layout/runtime/parsers/repository 和绑定到 manager 私有方法的回调。可将内容准备与静态检查收敛为 manager 内普通命名函数，让安装事务与来源更新直接复用；保持来源切换、恢复材料和失败回滚策略。来源物化的 [acquire.ts](../src/manager/acquire.ts) 与 revision 探测可归回 source 目录，但不机械搬动 ID、启用意愿和排序规则。
- [context.ts:21](../src/runtime/context.ts#L21) 仍手写较宽松的 Skill 契约，MCP 动态模块和配置也有 `unknown`/通用记录边界。可沿用已有 Shell/projection 的 SDK `Pick` 方式收紧 skills、plugin/effect 与 MCP 配置，在动态加载点完成一次确定的类型适配。测试替身应满足生产契约，避免为测试放宽生产接口；无需逐项再造端口层。

这些项目不要求修改任何来源格式规则。核心建议本轮未实施，尤其锁与来源所有权需要单独的事务回归。

## 客户端本轮实施范围

### 职责分离

将原管理面板中混合的工作拆为：

- `types.ts`：浏览器所需的窄 RPC 契约和客户端状态类型；不导入 Host 管理器。
- `usePluginBridge.ts`：列表、更新检查、变更操作、请求过期保护及错误状态；不处理语言翻译或 DOM。
- `PluginBridgePanel.tsx`：页面组合、检索/筛选及弹窗选择。
- 插件行、添加流程和操作确认分别为组件；不引入新的状态库或自建设计系统。
- 样式仍使用现有 CSS Module 与宿主 Token；侧边栏/主面板注册继续留在客户端入口。

### UI 和交互

1. 列表读取与更新检查独立完成；初次读取无需等待远端更新探测。
2. 刷新失败保留已有列表并显示可重试的持续提示；更新检查失败保留旧结果并明确提示，不把“检查失败”展示成“没有更新”。
3. 列表增加名称/ID/来源搜索、状态筛选、可见结果数和清空筛选后的恢复路径。
4. 共享来源更新前显示影响范围并由用户确认，再提交现有 `confirmShared` 参数。
5. 弹窗复用宿主 `Modal` 的焦点陷阱、Escape 与返回焦点，移除全局重复键盘拦截；来源输入避免在输入法组合期间提交。
6. 原位保留错误、进行中和诊断信息；窄面板下操作区和长文本能换行，不覆盖名称。

### 保持的行为

- 插件桥仍从侧边栏打开主区域，中文/英文名称和 RPC namespace 不变。
- 添加流程仍使用固定来源快照；取消和卸载的业务规则不改写。
- 开关、更新、卸载继续由 Host 原子生命周期处理；客户端不绕过任何错误或来源检查。
- 用户 profile、已安装数据、解析代码和协议模块不变。

## 目录结构建议

| 目录 | 判断 | 原因 |
| --- | --- | --- |
| `protocols`、`parser`、`composition` | 保持独立 | 分别承担格式规则、统一契约/编排、具体实现装配，合并会削弱可移除性。 |
| `types`、`shared` | 保持中立叶子 | 只容纳跨层的统一数据和基础能力；不能成为协议或 SDK 细节的收纳处。 |
| `source`、`store` | 保持独立 | 来源获取与磁盘事实、锁、事务生命周期不同。把 IO 都合并为 utils 只会隐藏边界。 |
| `manager`、`runtime` | 保持独立，收紧协调点 | 管理安装事实与实际运行实例应可分别测试；repository 的运行回调值得后续提回协调层。 |
| `web/host`、`web/client` | 保持分离 | 浏览器只依赖 DTO 和窄 RPC；Host 负责来源、事务和运行能力。客户端可在现有目录内按状态/流程拆分，不需要增加新的顶层目录。 |

文件变短不等于解耦。验收应关注依赖方向、状态所有权、可替换端口和故障隔离；避免新增只有转发作用的 facade、兼容别名或全局事件总线。
